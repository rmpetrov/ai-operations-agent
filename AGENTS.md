# AI Operations Agent — coding guardrails

- The current milestone permits the Sprint 4B offline runtime, the Sprint 4C opt-in OpenAI Responses API adapter verified exclusively through mocked provider responses, and the Sprint 4D local offline CLI demonstration, alongside the FastAPI + PostgreSQL backend. The CLI uses explicit workflows, a validated local queue allowlist, and deterministic simulation through the existing read-only runtime/tools; it cannot enable a provider or interpret arbitrary questions. **Live model invocations and live credential provisioning remain prohibited until separately approved.** Any future approved live evaluation must use synthetic operational data only.
- Keep runtime tools read-only and advisory; no autonomous writes or public deployment until separately approved.
- No new agent HTTP endpoints, arbitrary tools/SQL, hosted provider tools, or orchestration frameworks. Keep the provider disabled unless trusted local code explicitly configures it; questions and tool arguments cannot enable it or configure models, credentials, or connection targets.
- Treat `docs/ARCHITECTURE.md` and tests as the source of current scope and invariants.
- Preserve Alembic migrations; never silently create database tables at app startup.
- No hardcoded credentials outside explicitly local `.env.example` and docker-compose example.
- Do not expose the unauthenticated MVP on a public network.
- Keep PRs focused, include an API test for each behavior change, and explain technical tradeoffs.
- Never claim PostgreSQL integration passed without running it with `TEST_DATABASE_URL`.
- Leave generated reports, test DBs, and secrets out of git.
- Sprint 4E-1 additionally permits a reproducible offline evaluation harness using versioned synthetic scenarios, private in-memory SQLite, existing isolated PostgreSQL test fixtures, and optional request-local sanitized metadata. Generated reports remain ignored. This does not approve live model execution, live credential provisioning, development data resets, or natural-language workflow routing.
- Sprint 4E-2A additionally permits preparation and mocked verification of the controlled live smoke runner. Its default is an offline plan with no credential reads/client/network activity; the three fixed scenarios use private synthetic in-memory SQLite and the existing runtime/scorer. The real transport requires separate human approval plus explicit local opt-in and interactive confirmation, is blocked under pytest/CI, and must remain unexecuted during this milestone. No live credentials, real API requests/charges, `.env` changes, or natural-language routing are approved.
- Sprint 4E-2B narrows the first future separately approved live experiment to exactly `authorized-discovery`, preserving the original dataset/scorer, with at most two provider requests total (failed requests count), one read-only `list_queues` call, and 2,048 output tokens per request / 4,096 total. Discovery always terminates without assessment, retries, or repair. The three-scenario suite remains available only through verified SDK MockTransport injection; the public CLI cannot run the full suite. Offline default, process-only credentials, explicit opt-in, discovery-specific interactive confirmation, and pytest/CI real-transport blocks remain mandatory. Local request/token limits are not guaranteed API billing caps; no live-model behavior or API cost has been measured. This milestone authorizes code and mocked tests only, with no actual live execution, credential provisioning, billing changes, or `.env` changes.
